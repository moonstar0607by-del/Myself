# 前端搭建思路

## 框架
1. 结构层 - 内容有什么
2. 样式层 - 外观什么样
3. 行为层 - 怎么动
4. 数据层 - 约定说明数据格式

## 搭建结构 - HTML - 内容应该有什么
- 决策清单
    - 表单有哪些字段
        - 本质是**询问特定业务场景下，表单所承载的数据采集项的完整清单与属性定义**，也就是明确 "这个表单要收集哪些信息、每一项有什么填写规则"
        1. 通用基础字段
            - 系统字段：记录 ID、创建时间、更新时间、创建人、数据状态（正常 / 删除）（用户不可见，后台自动生成）
            - 主体信息字段：姓名 / 主体名称、联系电话、电子邮箱、地址、身份标识（身份证号 / 统一社会信用代码）
            - 辅助信息字段：备注、附件上传、操作说明
        2. 字段的核心属性
            - 只罗列字段名称是不完整的，通常还会同步说明每个字段的规则属性：
                - 显示名称：表单上呈现给用户的标题
                - 数据类型：文本、数字、日期时间、单选框、多选框、下拉选择、文件 / 图片上传
                - 必填性：必填项 / 选填项
                - 校验规则：格式校验（手机号、邮箱、身份证格式）、长度限制、数值区间、唯一性校验
                - 交互规则：默认值、是否可编辑、字段联动（如选择 “其他” 时弹出补充输入框）
        3. 不同业务场景的专属字段示例
            - 表单字段高度依赖业务场景，举几个典型场景的专属字段：
                - **用户注册表单**：用户名、登录密码、确认密码、短信验证码、邀请码、用户协议勾选
                - **差旅报销表单**：报销类型、出差起止日期、报销金额、发票号码、消费事由、行程明细
                - **商品订单表单**：商品名称、商品规格、购买数量、单价、总金额、收货地址、支付方式、物流单号
                - **员工入职表单**：部门、岗位、入职日期、学历、紧急联系人、工资卡号、社保信息
    - 每个字段用什么控件
        - 基于表单字段的数据类型、业务规则、使用场景，为每一个数据项匹配最合适的前端交互输入控件
        - 解决 “用户通过什么交互方式填写这条信息” 的问题，是表单设计从 “数据层” 落地到 “交互层” 的关键步骤
        1. 控件选型的核心原则
            - 控件选择不是随意匹配，有统一的判断标准：
                - **数据匹配原则**：控件输出的数据格式必须和字段定义的数据类型完全一致
                - **效率优先原则**：选项越少、填写越频繁，越要选用点击成本低的控件
                - **防错原则**：对格式要求强的字段，优先用自带约束的控件（比如日期用选择器而非手输）
                - **场景适配原则**：区分 PC 端 / 移动端、内网 / 外网、专业用户 / 普通用户做差异化选择
        2. 常见字段类型与控件的对应关系
            - 这是回答的核心主体，按字段类型给出标准选型：
                - **文本信息类字段**
                    - 短文本（姓名、标题、单号）：单行输入框
                    - 长文本（备注、说明、详情）：多行文本域；带格式要求的长文本用富文本编辑器
                    - 格式化文本（手机号、邮箱、身份证号）：带实时格式校验的单行输入框
                    - 密码类：密码输入框（支持明文 / 密文切换）
                - **选项类字段**
                    - 单选项≤5 个：单选按钮组
                    - 单选项＞5 个：下拉选择器；选项＞20 个时升级为带搜索功能的下拉选择器
                    - 多选项：复选框组；选项较多时用下拉多选框
                    - 层级选项（省市区、分类树）：级联选择器
                - **数值类字段**
                    - 普通数值（数量、年龄）：数字输入框（自带增减按钮）
                    - 金额：带货币单位与千分位格式的数字输入框
                    - 连续区间（价格区间、满意度评分）：滑块 / 双滑块
                - **日期时间类字段**
                    - 单个日期：日期选择器
                    - 日期范围：日期范围选择器
                    - 精确到时分秒：时间选择器 / 日期时间选择器
                - **文件与资源类字段**
                    - 单文件 / 多文件上传：文件上传控件
                    - 图片上传：支持预览、裁剪的图片上传控件
                - **状态与操作类字段**
                    - 二元状态（是否启用、同意协议）：开关组件 / 复选框
                    - 提交 / 重置操作：功能按钮
                3. 特殊场景的选型补充
                    - 只读展示字段：纯文本标签（不可编辑状态）
                    - 联动字段：主控件触发子控件显隐 / 可选值变化（比如选择 “其他” 时，弹出补充输入框）
                    - 可重复字段：支持新增 / 删除的动态行控件
    - value放英文还是中文
        - **表单控件中「实际提交的 value 值」与「用户可见的展示文本」的语言 / 编码规范选择**，核心要解决 “前端给后端传什么格式的数据、数据库存什么值” 的工程规范问题
            - 会混淆 **「label（展示标签）」和「value（提交值）」**
        1. 业界通用核心原则
            - **展示层（label）跟随用户语言，数据层（value）统一用英文 / 数字编码**
        2. 不同控件场景的具体规则
            - **选项类控件（单选 / 多选 / 下拉框，最常涉及这个问题）**
                - 标准方案：value 统一用英文小写枚举（或数字编码），label 展示中文。
                    - 性别选项：label 为「男、女」，对应 value 为 `male`、`female`
                    - 审核状态：label 为「待提交、已通过、已驳回」，对应 value 为 `pending`、`approved`、`rejected`
                    - 优势：后端枚举定义更规范、修改展示文案无需改动数据库、天然支持多语言切换、避免中文编码乱码问题。
            - **输入类控件（输入框、文本域）**
                - 不存在主动选择的问题：value 就是用户实际输入的内容，用户输入中文就是中文，输入英文 / 数字就是英文 / 数字；仅当字段有明确格式要求（如工号、邮箱、编码）时，才会限定为英文数字。
            - **系统隐藏字段**
                - 全部用英文 / 数字编码，绝对不用中文，比如表单类型、数据状态、操作标识等后台字段。
        3. 特殊场景的取舍
            - 可以用中文 value 的场景：仅面向内部的极简工具、无后端持久化的纯前端静态表单、一次性临时调研页，追求快速开发无需长期维护时可以图省事用中文，但不推荐作为常规方案。
            - 必须用英文 / 数字 value 的场景：有国际化需求、后端有统一枚举规范、需要对接多个系统、数据需要统计分析、长期迭代的正式项目。
    - lable和控件之间怎么关联
        - 本质是**如何实现表单文本标签与输入控件的语义绑定、交互联动与视觉对应**，核心要解决「用户清晰识别标签与输入项的对应关系」「点击标签可操作对应控件」「辅助设备能正确识别标签归属」三个目标
        1. 原生 HTML 的标准语义关联（底层核心原理）
            - 这是所有关联方式的基础，由 W3C 标准定义，同时实现交互联动（点击 label 聚焦控件）和无障碍识别。
                - **方式 1：for + id 显式绑定（最常用）**
                    给控件设置唯一`id`，给`<label>`设置`for`属性，值与控件 id 完全一致。两者在 DOM 结构中可以分离，布局灵活度最高。
                    - 示例：
                        <label for="user-name">用户名</label>
                        <input type="text" id="user-name" />
                    - 效果：点击 “用户名” 文字，光标自动聚焦到对应输入框；屏幕阅读器会将标签文本朗读为输入框的描述
                - **方式 2：label 包裹控件的隐式绑定**
                    直接把控件嵌套在`<label>`标签内部，无需写 id 和 for 属性，结构更简洁。
                    - 示例：
                        <label>
                            用户名
                            <input type="text" />
                        </label>
                    - 适用场景：单选框、复选框等小控件与文字紧挨着的内联场景；缺点是布局自由度低，复杂表单不推荐
                - **补充：选项组的分组关联**
                    对于单选按钮组、复选框组，除了每个选项绑定自己的 label，还需要用`<fieldset>` + `<legend>`给整组控件加一个总标签。
                    - 示例：
                    <fieldset>
                      <legend>性别</legend>
                      <label><input type="radio" name="gender" value="male" /> 男</label>
                      <label><input type="radio" name="gender" value="female" /> 女</label>
                    </fieldset>
        2. 前端 UI 组件库中的封装关联
            在 Ant Design、Element Plus 等主流组件库中，Form 组件已经内置了 label 与控件的自动绑定逻辑，无需手动写 id 和 for。
            - 典型用法：通过表单项组件的`label`属性传入标签文本，组件内部自动生成唯一 id、完成 label 与控件的绑定，同时处理对齐、必填标识、错误提示等布局逻辑。
                - 示例（Ant Design）：
                <Form.Item label="用户名" name="username">
                  <Input />
                </Form.Item>
                - 优势：开发者无需关心底层 id 的唯一性，组件自动处理语义关联、布局对齐、状态联动。
        3. 视觉与布局层面的关联
            除了代码语义绑定，视觉设计上也要强化标签与控件的对应关系，降低用户认知成本：
            - **位置规则**：主流布局分为「左标签右控件」（适合 PC 端宽表单）和「上标签下控件」（适合移动端、窄表单）；标签与对应控件必须在视觉上形成一组，组内间距远小于组与组之间的间距。
            - **对齐规则**：左标签布局建议标签右对齐，控件统一左对齐；上标签布局建议标签左对齐，保证视觉动线流畅。
            - **状态联动**：控件聚焦、报错、禁用时，对应 label 同步切换样式（如高亮、变红、置灰），强化关联感知。
        4. 特殊场景的关联处理
            - **无可见标签的场景**（如搜索框、图标输入框）：用`aria-label`属性给控件添加隐形标签，满足无障碍要求，例如`<input type="search" aria-label="搜索内容" />`。
            - **复杂复合控件**（如带按钮的输入框、日期范围选择器）：label 关联到主输入框，整体作为一个控件组处理。
            - **只读展示字段**：用标签 + 纯文本的形式对应，保持布局一致性。
    - 标签和组件是什么
        - 标签和控件是**表单界面里成对出现的两个核心元素**：
            - **标签（Label）**：负责「说明」—— 告诉用户 “这一项是填什么的”，是纯展示的文字说明。
            - **控件（Control / 表单控件）**：负责「输入」—— 用户用来填写、选择、操作数据的交互组件，最终会产生提交给系统的数据值。
        - 标签
            1. 核心定义
            标签是表单中用于**标注、说明对应控件用途的文本元素**，它本身不承载数据、不可编辑，只起信息提示和语义关联作用。
            2. 核心作用
                - 给用户做信息提示：明确旁边的输入区域对应什么业务含义（比如 “用户名”“联系电话”）。
                - 给系统做语义绑定：和控件关联后，点击标签就能触发对应控件（比如点 “记住我” 文字就能勾选复选框）；同时屏幕阅读器等无障碍工具能识别 “这个文字是描述这个输入框的”。
            3. 特点
                - 纯展示，不可交互编辑，没有自己的数据值。
                - 文本内容跟随用户语言（国内产品一般用中文）。
                - 分为两种形态：
                    - **可见标签**：表单上直接显示的标题文字，也是最常见的形态。
                    - **隐形标签**：没有可见文字，通过 `aria-label` 等属性给控件加语义说明，用在搜索框、图标按钮等不需要显示文字的场景。
            4. 常见误区
                标签≠字段名：字段是后台数据概念（比如数据库里的字段名 `user_name`），标签是前端展示概念（比如界面上显示 “用户名”），两者可以不一致。
        - 控件
            1. 核心定义
                控件是**用户与系统交互的界面载体**，在表单里专门负责采集用户输入、选择的信息，并把用户操作转化为程序能读取的数据值（value）。
            2. 核心作用
                承接业务字段的数据采集需求，让用户通过可视化的交互完成数据填写，最终输出对应的数据值提交给后端。
            3. 核心特点
                - **可交互**：用户可以点击、输入、选择、修改。
                - **有状态**：有正常、聚焦、禁用、报错、只读等多种状态。
                - **有值（value）**：每个控件都有对应的数据值，这是表单最终提交的核心内容。
                - **有类型**：不同类型的数据对应不同的控件形态，用来提升填写效率和准确率。
            4. 表单里常见的控件分类
                - 输入类
                    - 单行输入框、密码框、多行文本域、数字输入框
                - 选择类
                    - 单选框、复选框、下拉选择器、级联选择器、日期选择器
                - 操作类
                    - 提交按钮、重置按钮、开关
                - 文件类
                    - 文件上传、图片上传
